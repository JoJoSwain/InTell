## Why: three runtime bugs from Claude's code audit (27 Nov)
All three are in `apps/mobile/src/session/ExploringRuntime.ts`. Line numbers are at `c9e8eb3`.

### 1. Events interleave (audit MOB-1)
- **Who calls in:** location fixes, the 5 s session clock, voice-end events, lock-screen buttons and the overlay.
- **What goes wrong:** each calls `dispatch` or the director as soon as it arrives, and each waits on database writes, haptics, audio focus and decoding. So the calls interleave (`dispatch`, 545–699).
- **A story can start after Stop.**
  - `handlePlay` shows the overlay, then waits about a second for the haptic and `audioSession.start` (746–770).
  - A stop that lands in that second (Stop exploring, or the 15-minute or 3-hour end) finishes first.
  - `handlePlay` then carries on and starts the narration with no session and no overlay. The lock-screen Stop can't end it, because the session is already idle.
- **The app can lose track of a voice.**
  - `applyDirectorCommands` copies the voice map and returns the copy (`applyDirectorCommands.ts:73`). `applyCommands` assigns the result to `this.voices` (822).
  - When two calls overlap (a preload decoding during the narration's decode), the later one overwrites the map and drops the other's voice.
  - A later `stop` then misses that voice. For example, the remount after an interruption can start a second copy over the first.

### 2. Director commands are dropped (audit MOB-2)
Each `directorStep` records its output as already sent (`emit` sets `lastEmitted`, shared `director.ts:844`). So the caller must apply every step's commands.
- `directorSessionEffect` runs a `story` step, then a `sessionEffect` step, and applies only the second step's commands (800–812).
- `onNarrationProgress` runs a step and applies nothing (1027–1038).

Those decisions are never sent again. M6 has most layers off, so today this mostly loses preloads. In M7 it would lose the stem switch when a branch plays, Hush and ducking. The admin Simulator applies every step's commands (`apps/admin/src/lib/simulate/harness.ts:384`), so the phone would also sound different from it.

### 3. Pauses and interruptions (audit MOB-4, plus today's A10)
- `onInterruption("ended")` (1083–1113) resumes whenever the story is paused, whoever paused it. A listener's own pause can be undone by a call ending.
- **Today's A10 showed the opposite gap.** After a Clock alarm, the story didn't come back at all (`narr=none started=false`; evidence in `local/m6-walk-test/step5-A10.txt`). TECH_SPEC and the M1 acceptance expect a phone call to interrupt and then resume.
- **Wanted:**
  - A pause the app made for an interruption ends when the interruption ends, and the story resumes once, with one voice.
  - A pause the listener made stays until the listener resumes.

## Design (what the plan should confirm or improve)
### Serial queue
```ts
private chain: Promise<void> = Promise.resolve();
private serial(task: () => Promise<void>): Promise<void> {
  const run = this.chain.then(task, task);
  this.chain = run.catch(() => undefined);
  return run;
}
whenIdle(): Promise<void> { return this.chain; }
```
- **Every entry point goes through `serial()`:**
  - the fix and stop listeners
  - the engine's `onTick`, `onVoiceEnded`, `onNarrationProgress`, `onInterruption` and `onRouteChange`
  - the remote-command handler
  - the public `scanCode`, `stopExploring`, `togglePause`, `skipBack`, `reloadPacks`, `resetSessionKeepPacks`, `injectFix` and `injectNarrationEnded`
- **Split each public method in two:** a thin wrapper and a private `...Now()` body. Code already inside a queued task calls `...Now()` or `dispatch` directly, never `serial()`, which would deadlock. For example, `resetSessionKeepPacks` calls `stopExploringNow()`.
- **Engine callbacks enqueue and return at once** (`void this.serial(...)`), so an engine call that awaits its own callbacks can't deadlock. The fake engine's `stopAll` awaits voice-ended callbacks. Tests await `whenIdle()` instead of the callback's promise.

### handlePlay
After each await (haptics, `audioSession.start`, `audioSession.update`, `userPlay`), return unless `this.session.phase === "exploring"` and `this.session.playing?.fragmentId === play.fragmentId`. When it returns early, push the breadcrumb `play-abandoned <tail8>`.

### Director commands
- `directorSessionEffect` applies `[...first.commands, ...second.commands]` in one `applyCommands` call.
- `onNarrationProgress` applies its commands.

### Pause ownership
- Track who paused: the listener (overlay, lock screen) or the app (an interruption).
- First explain from `step5-A10.txt` why the story didn't return after the alarm. Then design the path:
  - **An app-made pause:** resumes once when focus returns.
  - **A listener's pause:** stays paused through an interruption. On the listener's resume, apply any deferred interruption-ended director step (keep the remount; filter suspend and resume as today).
- If the fix belongs in the native focus machine (`FocusController.kt` or `AudioSessionController.ts`), say so in the plan.

## Tests (fake engine)
1. A stop arrives while `handlePlay` waits on `audioSession.start`: no `playNarration` reaches the engine.
2. Two overlapping `applyCommands`: the narration voice stays tracked, and a later stop reaches it.
